### Highlights

- **[Company Update](#geohot-000006)**: tinygrad expects to receive both AMD bounty payments, totaling $800,000, but must complete the MLPerf submissions or return the money; the team is also preparing to announce its product launch.
- **[GPU Sales](#geohot-000109)**: New GPU orders will require compliance forms documenting the customer's intended use and deployment location; tinygrad plans to move toward GPU dropdown selectors and significantly higher GPU pricing, while customers can instead buy bare boxes and source GPUs themselves.
- **[GPT-OSS MLPerf](#geohot-000647)**: The GPT-OSS run is currently around the 128-minute target, with the team aiming to get below 119 minutes; throttling remains the main obstacle, and they want a sub-118-minute submission by the end of the next sprint.
- **[Multi-Machine Training](#geohot-000874)**: The team is targeting AMD's 71-minute GPT-OSS benchmark, with scheduling and communication overlap identified as key factors; Geohot explicitly says an ugly but non-cheating optimization is acceptable even if it cannot be merged upstream.
- **[Assembly Strategy](#qazalin-001319)**: Qazalin is shifting LLaMA optimization toward lifting assembly instructions into a CALL-based representation, with the goal of letting humans and LLMs reason about and optimize assembly more effectively; eventually, the LLaMA kernel should be generated by tinygrad.
- **[VIZ=2 Optimization](#geohot-001455)**: AMD's VIZ=2 kernel has a strong inner loop but wastes roughly 20–30% of execution time in a global-store epilogue; lifted assembly could interleave these operations and potentially raise utilization to roughly 70–90% MFU.
- **[CALLify Memory Model](#geohot-002120)**: CALLify now distinguishes three memory types—persistent global `BUFFER`, temporary in-CALL `ALLOC`, and externally passed `PARAM`; this simplifies the Tensor graph and has substantially reduced unnecessary memory use in the LLM.
- **[TensorCore Redesign](#chenyu-002763)**: TensorCore was redesigned to store only input/output dtypes and A/B/C layouts, deriving the remaining information directly from the hardware manuals; the new representation also simplifies the Python tensor-core emulator and removed about 70 lines of code.
- **[FP8 and MI300](#chenyu-003107)**: The team will retain the unusual FNUZ FP8 variants because MI300X supports FP8 tensor cores through them; the simplified tensor-core framework should also make adding smaller-dtype tensor cores such as FP4 and FP6 easier.
- **[MLPerf Direction](#geohot-003508)**: Geohot says the team appears poised to produce genuinely state-of-the-art MLPerf entries on AMD hardware, followed by the larger challenge of making the resulting MLPerf work broadly usable without requiring users to write their own kernels.

##### **Geohot** [[00:35:20](https://www.youtube.com/watch?v=m0nIr3dmWuw&t=2120)]
I had a productive week with CALLify. We now have three ways of creating memory. BUFFER is always bound to a Buffer object on a device; there is no longer such a thing as a bound or unbound BUFFER. ALLOC is an in-scope, non-persistent allocation. A BUFFER cannot exist inside a CALL; only an ALLOC can. To pass a BUFFER into a CALL, make it a CALL argument, where it becomes a PARAM.

##### **Geohot** [[00:36:18](https://www.youtube.com/watch?v=m0nIr3dmWuw&t=2178)]
Every allocation is therefore a BUFFER, ALLOC, or PARAM. A BUFFER is persistent and exists only at global scope. An ALLOC is temporary memory scoped to a CALL. A PARAM is memory passed in from outside the CALL, regardless of whether the source was a BUFFER or an ALLOC.

##### **Geohot** [[00:37:03](https://www.youtube.com/watch?v=m0nIr3dmWuw&t=2223)]
CALLify is much simpler now. We want CALLify to be as short as possible because it touches the Tensor graph and is a little slower. Two functions now rewrite the Tensor graph. The first is bufferize_outputs, which creates the physical output buffers for a realize. It creates buffers for the bases of tensors passed to realize, preserving the legacy behavior.

##### **Geohot** [[00:38:24](https://www.youtube.com/watch?v=m0nIr3dmWuw&t=2304)]
The other function is transform_to_call, which is essentially CALLify and is at the top of tensor.py. It creates the CALL for the graph being realized, pulls out BUFFERs and turns them into PARAMs, while ALLOCs stay inside the CALL. The only nuance is slicing large buffers: the slice stays outside the CALL so repeated calls on different slices can hit the cache. A future design could use a symbolic slice inside the CALL, but preserving current behavior is the only complexity that remains.

##### **Geohot** [[00:39:41](https://www.youtube.com/watch?v=m0nIr3dmWuw&t=2381)]
CALLify is now about 100 lines in Tensor. Some complexity moved into prepare, so my next work is prepare and rangeify. The stages are canonicalization, adding temporary buffers, rangeifying, and simplifying. Each step is clear now.

##### **Geohot** [[00:40:18](https://www.youtube.com/watch?v=m0nIr3dmWuw&t=2418)]
Bitcast now follows JAX semantics. Bitcasting float32 shape (4,) to int8 returns shape (4, 4). Bitcasting it back does not produce float32 shape (4, 1); it returns shape (4,). You cannot bitcast int8 shape (4, 8) directly to float32 shape (4, 2): the final dimension must exactly equal the dtype-size ratio. These are the rules from jax.lax.bitcast_convert_type.
